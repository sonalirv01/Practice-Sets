Q1 Explain your approach to designing a large-scale Laravel application. What folder structure and patterns do you use beyond the default MVC? ›
Architecture Hard Both Markets
★ Strong Answer
For a large-scale Laravel app, the default MVC structure breaks down fast. I organise around Domain-Driven Design (DDD) with a Service Layer separating business logic from controllers:
  • Controllers stay thin — they validate input and delegate to Services or Actions
  • Repository pattern abstracts data access so business logic never touches Eloquent directly
  • Action classes (single-responsibility) for complex operations
  • Events + Listeners for decoupled side effects
  • Data Transfer Objects (DTOs) to pass structured data between layers
php · Folder Structure + Service Layer 
// Folder structure beyond MVC:
app/
  Http/Controllers/    // Thin — input/output only
  Domain/
    User/
      Actions/         // Single-purpose business ops
      DTOs/            // Typed data transfer objects
      Repositories/    // Interface + Eloquent impl
      Services/        // Business logic orchestration
      Events/
      Listeners/
  Models/              // Eloquent models, minimal logic

// DTO using PHP 8 readonly properties:
class CreateUserDTO
{
    public function __construct(
        public readonly string $name,
        public readonly string $email,
        public readonly string $role = 'user',
    ) {}

    public static function fromRequest(CreateUserRequest $request): self
    {
        return new self(
            name: $request->validated('name'),
            email: $request->validated('email'),
            role: $request->validated('role', 'user'),
        );
    }
}

// Repository Interface (domain layer):
interface UserRepositoryInterface
{
    public function create(CreateUserDTO $dto): User;
    public function findByEmail(string $email): ?User;
    public function findOrFail(int $id): User;
}

// Eloquent Implementation (infrastructure layer):
class EloquentUserRepository implements UserRepositoryInterface
{
    public function create(CreateUserDTO $dto): User
    {
        return User::create([
            'name'  => $dto->name,
            'email' => $dto->email,
            'role'  => $dto->role,
        ]);
    }
}

// Service: orchestrates business logic, fires events
class UserService
{
    public function __construct(
        private UserRepositoryInterface $users,
        private NotificationService $notifications,
    ) {}

    public function register(CreateUserDTO $dto): User
    {
        if ($this->users->findByEmail($dto->email)) {
            throw new DuplicateEmailException($dto->email);
        }

        $user = $this->users->create($dto);

        event(new UserRegistered($user));

        return $user;
    }
}

// Thin controller — delegates everything:
class UserController extends Controller
{
    public function store(CreateUserRequest $request, UserService $service)
    {
        $user = $service->register(CreateUserDTO::fromRequest($request));
        return new UserResource($user);
    }
}
Ireland/UAE tip: Mention binding the interface in a ServiceProvider so you can swap Eloquent for a different data source without touching business logic. Enterprise roles love this.
Q2 How do you handle multi-tenancy in Laravel and what are the trade-offs between database-per-tenant vs shared-database approaches? ›
Architecture Hard Both Markets
★ Strong Answer
There are three main strategies:
  • Database-per-tenant — full isolation, easy backups, costly to scale
  • Schema-per-tenant (PostgreSQL) — good isolation, moderate cost
  • Shared DB with tenant_id column — cheapest, but requires rigorous Eloquent scoping
For the shared-DB approach, a Global Scope on every model is the safest guard against data leaks.
php · Global Scope Multi-Tenancy 
// 1. Tenant scope applied globally to all tenant-owned models
class TenantScope implements Scope
{
    public function apply(Builder $builder, Model $model): void
    {
        $tenantId = app(TenantContext::class)->getId();

        if ($tenantId) {
            $builder->where($model->getTable() . '.tenant_id', $tenantId);
        }
    }
}

// 2. Trait for any tenant-owned model
trait BelongsToTenant
{
    public static function bootBelongsToTenant(): void
    {
        static::addGlobalScope(new TenantScope());

        // Auto-assign tenant on creation
        static::creating(function ($model) {
            $model->tenant_id ??= app(TenantContext::class)->getId();
        });
    }
}

// 3. Usage in model
class Order extends Model
{
    use BelongsToTenant;
    // All queries now scoped to current tenant automatically
}

// 4. Middleware to resolve tenant from subdomain/header
class SetTenantContext
{
    public function handle(Request $request, Closure $next)
    {
        $host = $request->getHost();
        $slug = explode('.', $host)[0];

        $tenant = Tenant::where('slug', $slug)->firstOrFail();

        app(TenantContext::class)->setId($tenant->id);

        return $next($request);
    }
}

// 5. For DB-per-tenant: dynamic connection switching
class TenantDatabaseManager
{
    public function connectFor(Tenant $tenant): void
    {
        config(['database.connections.tenant' => [
            'driver'   => 'mysql',
            'host'     => $tenant->db_host,
            'database' => $tenant->db_name,
            'username' => $tenant->db_user,
            'password' => decrypt($tenant->db_password),
        ]]);

        DB::purge('tenant');
        DB::reconnect('tenant');
    }
}
UAE SaaS tip: Government and finance clients often mandate database-per-tenant for data residency compliance. Always discuss which approach you'd choose based on the regulatory environment, not just cost.
Q3 How do you implement CQRS in Laravel and when would you choose it over a standard repository approach? ›
Architecture Hard Ireland Focus
★ Strong Answer
CQRS separates write operations (Commands) from read operations (Queries). I use it when reads are far more frequent than writes, when the read model needs to be shaped differently from the write model, or when audit trails are critical. Laravel's Bus dispatcher is a natural fit.
php · CQRS with Laravel Bus 
// === COMMAND SIDE (Writes) ===

// Command — a value object describing intent
readonly class PlaceOrderCommand
{
    public function __construct(
        public int    $userId,
        public array  $items,
        public string $shippingAddress,
    ) {}
}

// Command Handler — only handles writes, returns void
class PlaceOrderHandler
{
    public function __construct(
        private OrderRepository $orders,
        private InventoryService $inventory,
    ) {}

    public function handle(PlaceOrderCommand $command): void
    {
        $this->inventory->reserveItems($command->items);
        $order = $this->orders->create($command);
        event(new OrderPlaced($order));
    }
}

// === QUERY SIDE (Reads) ===

// Query — describes what data is needed
readonly class GetOrderSummaryQuery
{
    public function __construct(
        public int $userId,
        public int $page = 1,
    ) {}
}

// Query Handler — direct DB read, no Eloquent models needed
class GetOrderSummaryHandler
{
    public function handle(GetOrderSummaryQuery $query): LengthAwarePaginator
    {
        return DB::table('orders')
            ->join('order_items', 'orders.id', '=', 'order_items.order_id')
            ->where('orders.user_id', $query->userId)
            ->select('orders.id', 'orders.status', DB::raw('SUM(order_items.total) as total'))
            ->groupBy('orders.id')
            ->paginate(20, page: $query->page);
    }
}

// === Dispatch from Controller ===
class OrderController extends Controller
{
    public function store(PlaceOrderRequest $req)
    {
        Bus::dispatch(new PlaceOrderCommand(
            userId: auth()->id(),
            items: $req->items,
            shippingAddress: $req->shipping_address,
        ));
        return response()->noContent(202);
    }

    public function index(GetOrderSummaryHandler $handler)
    {
        return $handler->handle(new GetOrderSummaryQuery(auth()->id()));
    }
}
When to use CQRS: High read/write ratio, complex reporting requirements, audit logging, event sourcing. Don't use it for simple CRUD apps — the overhead isn't worth it.

Q4 How do you diagnose and fix N+1 query problems in a complex production Laravel application? ›
Performance Medium Both Markets
★ Strong Answer
N+1 happens when you load a collection and then lazy-load a relationship for each item. In production I detect it with APM tools (Datadog, New Relic). In development, Laravel Debugbar or enabling strict mode catches it immediately.
php · N+1 Detection & Fix 
// ❌ N+1 Problem — 1 query for posts + 1 per post for user
$posts = Post::all();
foreach ($posts as $post) {
    echo $post->user->name; // query per iteration!
}

// ✅ Fix 1: Eager loading
$posts = Post::with('user')->get();

// ✅ Fix 2: Eager loading with specific columns (memory efficient)
$posts = Post::with(['user:id,name,avatar'])->get();

// ✅ Fix 3: withCount instead of loading full relationship
$posts = Post::withCount('comments')->get();
// $post->comments_count (no extra query when accessing)

// ✅ Fix 4: Nested eager loading
$orders = Order::with([
    'user',
    'items.product.category',
    'items' => function ($q) {
        $q->orderBy('created_at', 'desc');
    },
])->get();

// ✅ Prevent N+1 globally in AppServiceProvider (Laravel 10+)
use Illuminate\Database\Eloquent\Model;

public function boot(): void
{
    // Throws exception on lazy loading in non-production
    Model::preventLazyLoading(!app()->isProduction());
    Model::preventSilentlyDiscardingAttributes(!app()->isProduction());
}

// ✅ Debug: Log all queries with timing
DB::listen(function ($query) {
    if ($query->time > 100) { // flag slow queries > 100ms
        Log::warning('Slow query', [
            'sql'  => $query->sql,
            'time' => $query->time,
        ]);
    }
});
Pro tip: In API Resources, always define $this->whenLoaded() to avoid triggering lazy loads when a relationship isn't eager-loaded. This makes N+1 visible immediately during development.
Q5 Walk me through your caching strategy — what do you cache, where, and how do you handle invalidation? ›
Performance Medium Both Markets
php · Caching Strategies 
// 1. Simple remember — auto-cache with TTL
$products = Cache::remember('products.featured', now()->addHour(), function () {
    return Product::featured()->with('category')->get();
});

// 2. Cache tags — group related keys for bulk invalidation
$user = Cache::tags(['users', "user.{$id}"])
    ->remember("user.{$id}.profile", now()->addDay(), function () use ($id) {
        return User::with('profile')->findOrFail($id);
    });

// Invalidate everything tagged 'user.42' on profile update
Cache::tags(["user.{$id}"])->flush();

// 3. Cache stampede prevention with atomic locks
$data = Cache::remember('expensive.report', 3600, function () {
    return Cache::lock('expensive.report.lock', 30)->block(5, function () {
        return ReportService::generate();
    });
});

// 4. Event-driven cache invalidation
class InvalidateProductCache
{
    public function handle(ProductUpdated $event): void
    {
        Cache::tags(["product.{$event->product->id}"])->flush();
        Cache::forget('products.featured');
    }
}

// 5. HTTP response caching for public APIs
public function index()
{
    return response()->json($products)
        ->header('Cache-Control', 'public, max-age=300')
        ->header('ETag', md5($products->toJson()));
}

// 6. What NOT to cache
// ❌ User-specific volatile data (cart, session, notifications)
// ❌ Data that changes on every request
// ❌ Small queries that are already fast
Note: Cache tags require Redis or Memcached — they don't work with the file driver. Always mention this in interviews to show you understand the infrastructure requirements.

Q6 How do you implement API authentication at scale — Sanctum vs Passport vs JWT and why? ›
Security Medium Both Markets
php · Sanctum SPA Auth + Token Rotation 
// === Sanctum (SPA / Mobile) ===
// Best for: first-party SPA and mobile apps

// Issue token with abilities (scopes)
$token = $user->createToken(
    name: 'mobile-app',
    abilities: ['orders:read', 'profile:update'],
    expiresAt: now()->addDays(30),
);

// Check ability in controller
if (!$request->user()->tokenCan('orders:read')) {
    abort(403);
}

// Revoke all tokens on logout
$user->tokens()->delete();

// === Passport (OAuth2 for third-party) ===
// Best for: public API, third-party integrations
use Laravel\Passport\HasApiTokens;

// Authorization code flow for third-party apps
// routes/api.php
Route::middleware('auth:api')->group(function () {
    Route::get('/user', function (Request $request) {
        return $request->user();
    });
});

// === JWT Considerations ===
// Best for: stateless microservices
// ⚠️ WARNING: JWTs cannot be revoked before expiry
// Mitigation: short TTL (15min) + refresh token rotation

class AuthController
{
    public function refresh(Request $request)
    {
        // Invalidate old refresh token (rotation)
        RefreshToken::where('token', $request->refresh_token)
            ->firstOrFail()
            ->delete();

        // Issue new pair
        $accessToken  = JWTAuth::fromUser(auth()->user());
        $refreshToken = Str::random(64);

        RefreshToken::create([
            'user_id'    => auth()->id(),
            'token'      => hash('sha256', $refreshToken),
            'expires_at' => now()->addDays(7),
        ]);

        return response()->json([
            'access_token'  => $accessToken,
            'refresh_token' => $refreshToken,
            'expires_in'    => 900, // 15 minutes
        ]);
    }
}
Decision matrix: First-party SPA → Sanctum with cookies. Mobile app → Sanctum tokens. Third-party OAuth2 → Passport. Microservices → JWT with short TTL. Never use JWT just because it sounds modern.

Q8 How do you handle database migrations safely in a high-traffic production environment? ›
DevOps Hard Both Markets
★ Strong Answer
The key principle is the expand/contract pattern: never make a breaking change and a code change in the same deployment. Break it into two separate deploys separated by however long it takes to be safe.
php · Safe Migration Patterns 
// ❌ DANGEROUS: Rename column in one deploy
// Breaking — old code uses 'username', new code uses 'name'

// ✅ SAFE: Expand/Contract over 3 deploys

// Deploy 1: Add new column (non-breaking)
class AddNameToUsersTable extends Migration
{
    public function up(): void
    {
        Schema::table('users', function (Blueprint $table) {
            $table->string('name')->nullable()->after('username');
        });
    }
}

// Deploy 2: Code writes to BOTH columns, reads from old
// (data is kept in sync)
class User extends Model
{
    protected static function boot(): void
    {
        parent::boot();
        static::saving(function ($user) {
            $user->name = $user->name ?? $user->username;
        });
    }
}

// Backfill existing rows in batches (not one giant update)
class BackfillNameFromUsername extends Migration
{
    public function up(): void
    {
        User::whereNull('name')->chunkById(500, function ($users) {
            foreach ($users as $user) {
                $user->update(['name' => $user->username]);
            }
        });
    }
}

// Deploy 3: Remove old column (now safe)
class DropUsernameFromUsers extends Migration
{
    public function up(): void
    {
        Schema::table('users', function (Blueprint $table) {
            $table->dropColumn('username');
        });
    }
}

// ✅ Adding index without locking the table (MySQL)
class AddIndexToOrdersStatus extends Migration
{
    public function up(): void
    {
        // ALGORITHM=INPLACE, LOCK=NONE — no table lock on MySQL 8+
        DB::statement('
            ALTER TABLE orders
            ADD INDEX idx_status_created (status, created_at)
            ALGORITHM=INPLACE, LOCK=NONE
        ');
    }
}
CI enforcement: Use the never-drop-columns rule in your migration linter or add a custom Artisan command that checks for destructive operations before allowing deployment to production.

Q9 You've inherited a legacy Laravel 5 codebase with no tests and spaghetti code. How do you modernise it without halting feature delivery? ›
Leadership Hard Ireland Focus
★ Strong Answer
Use the Strangler Fig pattern — build the new system around the old one incrementally. Never rewrite everything at once. The approach:
  • Week 1–2: Add characterisation tests — document what the system does now, not what it should do
  • Week 3+: Identify the highest-churn, highest-risk modules and refactor those first
  • Ongoing: New features go into the clean architecture; legacy code is touched only when business value justifies it
php · Characterisation Tests + Incremental Refactor 
// Step 1: Characterisation test — capture CURRENT behaviour
// Don't ask if it's correct, just document what it does
it('calculates order total the way it does today', function () {
    $order = createLegacyOrder(['items' => ['A', 'B'], 'discount' => 10]);

    // This test will fail if a refactor changes the output
    expect(calculateTotal($order))->toBe(90.00);
});

// Step 2: Wrap legacy code behind an interface
// New code calls the interface; old code is the initial implementation
interface OrderCalculatorInterface
{
    public function calculate(Order $order): float;
}

class LegacyOrderCalculator implements OrderCalculatorInterface
{
    public function calculate(Order $order): float
    {
        // Wraps existing legacy function — don't touch it yet
        return calculateTotal($order);
    }
}

// Step 3: Feature flags to shadow-test new implementation
class NewOrderCalculator implements OrderCalculatorInterface
{
    public function calculate(Order $order): float
    {
        $legacy = app(LegacyOrderCalculator::class)->calculate($order);
        $new    = $this->computeWithNewLogic($order);

        if ($legacy !== $new) {
            // Log discrepancy, don't fail — gather data first
            Log::warning('Calculator mismatch', [
                'order_id' => $order->id,
                'legacy'   => $legacy,
                'new'      => $new,
            ]);
        }

        return feature('new-calculator') ? $new : $legacy;
    }
}

// Step 4: Upgrade Laravel version incrementally
// L5 → L6 → L8 → L10 → L11, one major version at a time
// composer require laravel/framework:^6.0 — fix deprecations, test, ship
// Repeat. Jumping multiple majors at once is how migrations fail.
The real answer interviewers want: Show you won't request a 6-month freeze to rewrite everything. Demonstrate patience, pragmatism, and that you can deliver new features while improving the codebase simultaneously.
Q10 Describe a technically complex decision you made in Laravel that you'd approach differently today. ›
Leadership Medium Both Markets
★ Strong Answer — Example Framework
This is a growth and self-awareness question, not a technical one. The interviewer is testing whether you can:
  • Reflect honestly without being defensive
  • Explain technical reasoning, not just the outcome
  • Show you've grown — what you'd do differently and why
Use a real example. Below is a common real-world scenario to draw from or adapt:
php · Example: Over-engineered Queue Architecture 
/*
  SITUATION: 3 years ago, I built a notification system
  using custom job chaining and dynamic queue routing.
  I thought it was elegant. It became a nightmare.
*/

// ❌ What I built — clever but undebuggable
class NotificationOrchestrator
{
    public function dispatch(User $user, string $event): void
    {
        $chain = collect($user->notificationChannels())
            ->map(fn($channel) => new DynamicNotificationJob($channel, $event))
            ->toArray();

        // Chain of dynamically determined jobs. When one fails,
        // tracing it in Horizon was nearly impossible.
        Bus::chain($chain)->dispatch();
    }
}

// ✅ What I'd do today — explicit, observable, boring
class NotificationService
{
    public function notifyUserRegistered(User $user): void
    {
        // Explicit named jobs — immediately clear in Horizon/logs
        SendWelcomeEmail::dispatch($user)->onQueue('emails');

        if ($user->sms_opt_in) {
            SendWelcomeSms::dispatch($user)->onQueue('sms');
        }

        if ($user->push_token) {
            SendWelcomePush::dispatch($user)->onQueue('push');
        }
    }
}

/*
  LESSON: I over-engineered for flexibility I never needed.
  Boring, explicit code is easier to debug at 2am during
  an incident. I now default to simple until complexity
  is genuinely required.
*/
Structure your answer as: Situation → What I decided and why it seemed right → What broke/was painful → What I'd do instead → What principle I took away. Keep it under 3 minutes when spoken.
